# Repair 18 - Full Backend Audit - Synthesis

## 1. Header: scope, method, evidence standard

**What this document is.** This is the synthesis of the six-track full backend audit ordered by the founder on 2026-10-17. It is the evidence for his condition for the Repair 18 redesign autonomy: "the back end functions exactly and has all the features that I asked for." Where the backend meets that condition, this document says so and points at the proof. Where it does not, the gap is named, numbered, and given a disposition. Nothing found by any track is silently dropped.

**Scope.** Every server-side tree in the repo:

- `apps/opal_core/lib/opal_core/` - the Elixir core contexts (all top-level folders and files).
- `apps/opal_core/lib/opal_core_web/` - router, 55 controllers, 3 channels, 7 plugs, endpoint, socket, presence, telemetry.
- `services/opal_ai/` - the Python AI worker service (23 files, 2,992 lines).
- Repo-root `config/`, `apps/opal_core/config/`, `infra/`, `scripts/` (server and ops subset), `packages/`, root `tests/`, and the root Makefile.

**Method.** Six read-only audit tracks, all run at the same point in history: the Repair 17 tip, commit `1892e5d6`, in worktree `wt-repair18` on branch `muse/repair-18`. No source files were edited by any audit track.

- Track 1 - identity and people: `coordination/repair18/audit-1-identity-people.md` (31 modules).
- Track 2 - coordination core: `coordination/repair18/audit-2-coordination-core.md` (488 files, 493 modules).
- Track 3 - surfaces and services: `coordination/repair18/audit-3-surfaces-services.md` (ai, intelligence, bookings, calls, lives, places, push, email, artifacts, observability, infrastructure, mix tasks, plus the leftover-folder sweep).
- Track 4 - web, opal_ai, misc trees: `coordination/repair18/audit-4-web-ai-misc.md` (282-route truth table, channels, services/opal_ai, config, infra, scripts, packages, root tests).
- Track 5 - ask registry: `coordination/repair18/audit-5-ask-registry.md` (88 asks, ASK-1 to ASK-88, with sources; 16 never-carried gaps; 12 gated or banned correctly-absent items).
- Track 6 - connectors: `coordination/repair18/audit-6-connectors.md` (25 integrations classified working / founder-gated / not wired, with live staging-log evidence).

This synthesis is also consistent with the coordinator registers in `coordination/repair18-status.md`: the blind-spot register (BS-1 to BS-17), the leapfrog debt register, the backend-change justification log, and the Division B rulings. Where a track finding and a register entry describe the same defect, this document carries one gap entry and names both sources. Division B design findings (tracks B1 to B5 in the same status file) are cited where they intersect the gaps list.

**Evidence standard (founder law, applied by every track).** A capability counts as available only with live evidence or a wired path: a production caller in `lib/`, a live provider response in a log, a recorded live-verify artifact, or a live endpoint answer. Code existence alone is not availability. A module that is exercised only by tests is reported as test-only, however good its tests are. A code path that exists but was never exercised live is reported as unproven, not working. Env values were never read or printed by any track - presence or absence of variable NAMES only.

**How to read this document.** Section 2 is the map: every tree, its size, and its state census, with pointers to the track reports that carry the full tables. Section 3 is the verdict table the founder asked for: all 88 asks, each marked against the code. Section 4 is the gaps list: every defect, numbered, with a disposition inside Repair 18 or a named reason it stays founder-visible and outstanding. Section 5 is the integrations evidence. Section 6 is the law verdicts. Section 7 states plainly what this audit does not prove.

**Headline verdict.** The backend core is real: the plan authority, the transition gate for the main plan family, the consent ledger, the messaging boundary, the location pipeline, the DeepSeek path in the thread pipeline, and the honesty pattern (disabled means disabled, never a fabricated success) all check out in code and, where cited, in live evidence. The backend does NOT yet meet the condition in full. The walk failures the founder found in under two minutes are real backend and contract defects, not user error: attendance was invented by three surfaces because no backend counter was ever projected, two non-interoperating change systems let an accepted 8 PM change read back as 7:30 PM, duplicate forming plans have no dedupe and no lifecycle, and Center answered from a parked template with stale context. Beyond the walk catalog, a whole plan family (group and family plans) sits outside the gyroscope, 175 coordination modules are a pure library layer with no direct product entry point, and 16 asks were never carried into any repair at all. Each of those is in Section 4 with its disposition.

The Python service carries the same law in its module headers (no relationship scores, proposals only). A whole-product certification requires each future surface to keep passing the same check; within this audit's scope, the ban holds.

### 6.3 Wallet gate (loads gated on keys plus legal review) - HELD

Wallet loads are correctly gated off in both places they could open: `Wallets.load` returns disabled without a Stripe key and returns the legal-approval disabled message unless the loads-enabled env flag is exactly true (the test path additionally requires an explicit test flag AND the test environment), and `StripeCheckout.create_session` applies the same two gates before creating a session and never invents payment success; the webhook credits through the same idempotent load path. Spends and credits are live ledger operations, so balances can only originate from credits, splits, and test loads. The gate holding does not excuse the webhook defects beside it (GAP-23): they are safe today only because the gate flag is closed, and they must be fixed before any enablement. The gate is founder law working as written; the defects are filed against the day it opens, not against today.

### 6.4 Honesty (no fake bookings, confirmations, orders, or success) - BOOKINGS PASS; the named fake-success exceptions are these, and only these

Bookings pass cleanly. The provider behaviour states the law in its moduledoc (return disabled when credentials are absent, never invent confirmation numbers); the booking schema only ever sets a confirmation number from a live provider response or the test-only mock; OpenTable book and cancel always refuse to a call-to-book handoff; Duffel is a real client whose test mode is explicit-only; the mock asserts test-only on every callback; and with no ready provider the booking service returns an honest disabled message with no confirmation-shaped fields. At the HTTP layer, Track 4 verified the same pattern product-wide: no stub or fake-success controller exists anywhere, and every disabled path returns an explicit disabled, unavailable, or forbidden shape.

The fake-success exceptions found anywhere in the backend are exactly these six, each already numbered as a gap - there are no others in the audit record:

1. GAP-13 (BS-4): the Deepgram canned transcript, persisted as a real voice message body when unkeyed. The clearest honesty violation in the audit.
2. GAP-20 (BS-1): the TimelineAdjustSheet fake save - a "Time updated" note with no API call behind it.
3. GAP-21 (BS-15): the OpenTable search query-echo, which would present the caller's own query as a result the day a key is added. Inert today.
4. GAP-14 (BS-5): Sentry capture returning `{:ok, :queued}` for reports that go nowhere - fake success at the observability boundary, readable as healthy on the health surface if a DSN were set. Inert today (no DSN on staging).
5. GAP-17 (BS-17, FCM half): FCM false-ready - configured reported for a credential the sender never uses, aimed at an endpoint that no longer exists.
6. GAP-24 (BS-8): the opportunity evaluate fixture default - a live route returning fixture-backed results unlabelled in the response. (Its sibling, curate's fixture fallback, is labelled and is therefore an honesty pass with a product caveat, not an exception.)

Two further items sit at the edge of this law and are reported as what they are, not inflated into violations: the consent capability that can be granted but never executes (GAP-33) is honest in code - its execution status says `:absent` - and is a product-list question, not a fake; and the founder seed's fixture surfaces (GAP-12) are flag-gated and internally identifiable, which is the compliant shape, with idempotency as the defect.

### 6.5 Per-account isolation (each account's Opal is a separate mind) - PRESENT, with the 3 partials from Track 1

Present-and-real in the main paths, on strong evidence: consent lists, revokes, and validation all enforce the owning user; relationship reads filter by user and the reverse relationship label is never exposed by construction; financial rows are one per user behind a unique constraint; memory store and recall are scoped by owner, active, and private; the product session's public user projection exposes only id, display name, and handle; and SocialMemory makes isolation a type - reads require a scoped struct carrying the account id, and dismissing another account's nudge returns wrong-account. The 3 partial spots, all from Track 1 and all named as gaps, are:

1. GAP-30: `connected_peer_ids` isolates by post-filtering a global query instead of by query - correct output today, wrong shape, with a silent contact-loss failure past 100 establishments.
2. GAP-31: group aggregate and financial context-slice functions accept their inputs without a requester membership check or a trust re-check - internal callers only today, so defense-in-depth, not a live leak.
3. GAP-28: the dedicated Access enforcement layer is not wired into API responses, so isolation for plan and person context depends on each module scoping its own queries rather than on the layer whose stated job it is. The queries checked do scope correctly.

The correct statement is: no cross-account disclosure was found anywhere in this audit, and the isolation architecture is real - with three named places where it holds by caller discipline rather than by construction.
