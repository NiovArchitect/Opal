# Repair #18 - cumulative founder regression suite

The permanent home of the founder regression suite. Law (founder,
2026-10-17): if he found it once, it is tested forever. Every
founder-reported failure from every walk and repair cycle is a
permanent case here, run at the real user path, per the
real_user_path_acceptance standard: same entry point the founder
walks, two distinct authenticated sessions where accounts matter,
varied phrasing, and read-back of every mutated object on EVERY
surface that shows it.

## Layout

- `run.mjs` - the suite runner (discovers cases, reports per case
  pass/fail with the failing surface named, exit 0/1/2).
- `lib/harness.mjs` - sessions, API client, founder seed, endpoint
  helpers, soft assertions, attendance/conflict extractors.
- `lib/generate-case-index.mjs` - regenerates `cases.json` and
  `CASE_INDEX.md` from the regression catalog.
- `cases/` - one file per executable case (`*.case.mjs`). Division B
  and C cases plug in here; see `cases/template.case.example.mjs`.
- `CASE_INDEX.md` / `cases.json` - the generated index of all 82
  permanent cases (case id, title, theme, automatable vs
  phone-checklist), generated from
  `coordination/repair18/regression-catalog.md`. Do not edit by hand;
  re-run the generator.
- `FIRST_RUN.md` - the recorded first run of the F18 cases.
- `results.json` - machine output of the most recent local run
  (regenerated by every run; not evidence by itself).
- `rendered/` - the RENDERED stage (standing gate, founder
  2026-10-17: NO WALK WITHOUT RENDERED PROOF). Real Chromium, real
  served app, phone viewport 390x844, every primary surface in dark
  AND light, plus the Walk #4 rendered cases W4-02 / W4-03. See
  `rendered/README.md`. API green + rendered red = not
  handable-over.

## Running against a live staging stack

The staging stack is the Mac opal-walk stack (backend + web served at
the exact tip under test). The API-level cases in this suite talk to
the backend the web client talks to, with the same request shapes
the client sends (productClient.ts), so set the base URL and provide
seed-mode sessions:

```sh
# Backend base URL of the stack under test (no trailing slash).
export OPAL_API_BASE=http://127.0.0.1:4000

# Sessions: the minted walk-session file (same file the _repair10
# and _consumer_reality_gate scripts consume). Roles a and b are two
# DISTINCT authenticated sessions - two-party cases require both.
export OPAL_MINTED_SESSIONS_JSON=/tmp/opal_minted_walk_sessions.json

# Seed mode: provisions the founder seed for session A first
# (communication + graph commitment), exactly what
# opal_founder_seed=1 does on the walk path. Real backend records,
# nothing scripted (Repair #17 law).
export OPAL_SEED_MODE=1

node shots/regression/run.mjs                 # all executable cases
node shots/regression/run.mjs --case FR-18-04 # one case
node shots/regression/run.mjs --list          # list executable cases
```

Walk-path runs additionally open the web app the way the founder
does - `?opal_founder_seed=1&opal_dev=1` (badge law) - for the
browser-level and phone-checklist cases in the index. Those cases
are listed in CASE_INDEX.md with their class; the phone-only four
(FR-05-02, FR-11-07, FR-06-03, FR-15-02) stay on the founder phone
checklist by name and are never silently dropped.

Exit codes: 0 = all selected cases pass; 1 = at least one case FAIL
(a defect reproduced, failing surfaces named in the output);
2 = harness error (the suite itself could not run - never report
this as a product result).

## Running the API-level subsets locally

Against a local backend (dev env, Postgres 16):

```sh
export PATH=~/workspace/elixir/bin:$PATH
export MIX_DEPS_PATH=/tmp/opal_deps
cd apps/opal_core && mix phx.server   # serves :4000

# In another shell, from the repo root:
export OPAL_API_BASE=http://127.0.0.1:4000
export OPAL_SEED_MODE=1

# Session provisioning for local/dev stacks only: fresh sessions
# through the product activation API using the synthetic SMS
# provider's fixture numbers. NEVER against a production_sms stack.
export OPAL_SESSION_PROVISION=synthetic
export OPAL_PHONE_A=+12025550101 OPAL_PHONE_B=+12025550102

node shots/regression/run.mjs
```

Direct tokens also work: `OPAL_TOKEN_A` / `OPAL_TOKEN_B` (plus
optional `OPAL_USER_A` / `OPAL_USER_B`).

For FR-18-03, the stack under test must have the LLM key configured
in the server env (`OPAL_LLM_API_KEY`, name only) for the engagement
assertion to be meaningful; without it the case reproduces the walk
exactly (template replies, llm_called false) and fails by design.

## Adding a case (Divisions B, C, and Repair #19+)

1. The finding gets a permanent FR id in the catalog first (never
   renumber existing cases).
2. Copy `cases/template.case.example.mjs` to
   `cases/<id>-<slug>.case.mjs` and implement it against the API
   output the surfaces render (contract law: shape + values, not
   internal state).
3. Regenerate the index:
   `node shots/regression/lib/generate-case-index.mjs`
4. A case is proven only after 3 varied runs plus one adversarial
   pass on the live staging stack at the exact tip under test.

Rendered cases (Walk #4 onward) live in `rendered/cases/` instead:
copy the shape of `rendered/cases/w4-02-thread-composition.case.mjs`
(id, title, theme, class "R (rendered)", surfaces, `run(rctx)`),
and they are discovered by `rendered/run-rendered.mjs`. Their ids
are also listed in `cases.json` / `CASE_INDEX.md` - NOTE: those two
files are generated from the coordination catalog, which does not
yet carry the W4 rows; until the coordinator adds catalog rows for
W4-02 / W4-03, re-running the generator will drop them from the
index (the case files themselves are permanent). The additions are
listed precisely in
`coordination/repair18/phase2-reg-c-report.md`.
